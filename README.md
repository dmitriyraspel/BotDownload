# BotDownload

Telegram-бот для загрузки отдельных видео и MP3 с YouTube, Instagram и TikTok.

> **Состояние ветки `restore/verified-691-tests`: код требует приведения к утверждённой архитектуре v1. Это исходная кодовая база для доработки, а не готовый к публичному запуску сервис.** Старые тесты подтверждают поведение старой реализации, но не соответствие новым требованиям. Не включайте реальный `yt-dlp` вне защищённого постоянного `tgbot-worker.service`.

## Единственные утверждённые требования

1. [Техническое задание v1](docs/TECHNICAL_SPEC_V1.md) — функциональность, конфигурация, эксплуатация, очередь и IPC.
2. [Политика безопасности v1](docs/SECURITY_POLICY_V1.md) — обязательные ограничения безопасности; при расхождении имеет приоритет над ТЗ.

README — руководство по проекту и эксплуатации, **не третий нормативный документ**. Исторические материалы этапов разработки из `docs/` удалены. Исходный код и исторические тесты тоже не имеют приоритета над двумя документами.

## Целевая архитектура v1

- **Debian 13**, Python в `venv`, `yt-dlp`, FFmpeg/ffprobe, SQLite, `config.yaml` и локальный `.env`.
- Два постоянных системных юнита: `tgbot.service` (Telegram, проверка URL, очередь, SQLite, квоты, отправка) и `tgbot-worker.service` (`inspect`, `yt-dlp`, FFmpeg). Оба работают под одним непривилегированным Linux UID `tgbot`.
- IPC между юнитами — **Unix domain socket + JSON Lines** (версия 1, `inspect`, `download`, `cancel`, `status`). SQLite читает и изменяет **только основной бот**; worker не открывает БД.
- Worker и все дочерние процессы ограничены systemd: `IPAddressDeny=127.0.0.0/8`, `IPAddressDeny=::1/128`. Остальные частные сети, link-local и Fake-IP `198.18.0.0/15` в v1 **не блокируются**. Запрет `PrivateNetwork=yes` и динамических `systemd-run` для рабочего процесса. Локальный Bot API на `127.0.0.1:8081` доступен основному боту.
- Допустимые *исходные* пользовательские URL и параметры перечислены в §4.1 ТЗ. Проверка `validate_url()` должна выполняться до **любого** вызова `yt-dlp`. API/CDN-запросы самого `yt-dlp` не обязаны оставаться в пользовательском списке доменов, но подчиняются защите worker.
- Не более **одной активной загрузки/обработки**, до 20 ожидающих загрузок, 30 минут ожидания. `inspect` может идти параллельно единственной загрузке, но внутри защищённого worker.
- Если `inspect` не дал достоверных качеств, пользователю предлагаются **только две кнопки**: «Скачать видео» и «Скачать аудио». После загрузки — обязательная проверка медиа, включая лимит 7200 секунд.
- Рабочая директория проекта — `botdownload` (абсолютный путь выбирается при установке); готовые медиа — `files/` внутри неё, параметр `storage.files_dir: "files"`. `storage.keep_downloaded_files: false` — удалять готовый файл **после успешной доставки**, `true` — сохранять; частичные и повреждённые файлы удалять всегда.
- `telegram.api_mode: local` по умолчанию; `cloud` — альтернативный ручной режим, автоматического переключения нет.

Полный контракт IPC, допустимые URL, лимиты, восстановление и приёмочные проверки определены в двух документах. Не заменяйте их предположениями из старого кода.

## Что в текущей ветке ещё не соответствует ТЗ

**Обязательная работа ИИ-разработчика до развёртывания:** существующий `bot/main.py` запускает внутренний `OfflineWorkerSupervisor`, а старый `bot/worker_ipc.py` содержит офлайн-операции и путь чтения SQLite из worker. В репозитории также присутствуют экспериментальные namespace/gateway-компоненты и тесты прежней архитектуры. Это **не** реализация утверждённого IPC v1 и **не** доказательство изоляции. Разработчик должен переработать или убрать устаревшие пути вызовов, а не активировать их для реальной загрузки. Старый пример systemd-юнита удалён, поскольку он запрещал весь IP-трафик и не соответствовал v1. Новые **оба** юнита нужно реализовать и проверить по ТЗ.

Текущие `config.yaml` и `bot/config.py` ещё используют наследуемый `storage.download_dir` и не реализуют весь контракт `storage.files_dir` / `storage.keep_downloaded_files`. Это задача реализации, **не** повод менять утверждённую конфигурацию. Не добавляйте новые поля в работающий старый конфиг до одновременного обновления его валидатора.

`python -m bot` допустим для диагностики кода. Он **не является способом запускать реальные скачивания** в обход постоянного защищённого worker. Не использовать ветку для публичного запуска до прохождения приёмки из §21 ТЗ и §10 политики.

## Подготовка окружения разработчика

Следующие команды выполняются **в терминале Debian, из корня клонированного проекта**; они не включают реальную загрузку.

1. Проверить расположение проекта и Python:

   ```bash
   pwd
   python3 --version
   ```

2. Создать виртуальное окружение (папка `.venv/` исключена из Git):

   ```bash
   python3 -m venv .venv
   ```

3. Установить зависимости проекта для разработки:

   ```bash
   .venv/bin/python -m pip install -r requirements-dev.txt
   ```

4. Создать локальный файл для секретов, **не отправлять токен ни в чат, ни в Git**:

   ```bash
   cp env.example .env
   ```

   Укажите секрет через локальный редактор. Административные Telegram ID внесите только локально.

5. Проверить `ffmpeg`, `ffprobe`, `yt-dlp` и доступность окружения:

   ```bash
   ffmpeg -version
   ffprobe -version
   .venv/bin/python -m bot.doctor
   ```

   `doctor` — предварительная диагностика старого кода; успешное выполнение **не доказывает** сетевую защиту.

6. Запустить локальные офлайн-тесты старой кодовой базы:

   ```bash
   .venv/bin/python -m pytest -q
   ```

   Их прошлое количество и прежние PASS не являются приёмкой v1.

Отдельный локальный Telegram Bot API Server должен быть установлен и настроен оператором; данный репозиторий его не устанавливает.

## Безопасное обновление установленного сервиса (Debian 13)

**Внимание:** это порядок *для сервиса после реализации двух systemd-юнитов*. На текущей ветке до доработки он не гарантирует работоспособность. Команды `systemctl` выполняет администратор VPS, остальные — из рабочего каталога установленного проекта. Не удаляйте `.env`, `config.yaml`, `files/`, БД, журналы и резервные копии.

1. **Проверить сервер, каталог, Git и текущие изменения.** Например, для установки в `/opt/BotDownload`:

   ```bash
   cd /opt/BotDownload
   pwd
   git branch --show-current
   git status --short
   git rev-parse HEAD
   ```

   Запишите SHA коммита для возможного отката. При неожиданных локальных изменениях остановитесь и выясните их назначение: не выполняйте `reset --hard` или очистку каталогов.

2. **Остановить оба сервиса.** Сначала предупредите пользователей о возможном прерывании задач:

   ```bash
   sudo systemctl stop tgbot.service tgbot-worker.service
   sudo systemctl status tgbot.service tgbot-worker.service --no-pager
   ```

   Ожидается, что сервисы не работают. Если есть незавершённые задачи или отказ остановки, выясните состояние прежде, чем продолжить.

3. **Сделать резервную копию SQLite.** Путь БД определяется фактической установкой; пример для унаследованного расположения `data/bot.sqlite`. Для команды требуется установленная утилита `sqlite3`:

   ```bash
   mkdir -p backups
   sqlite3 data/bot.sqlite ".backup 'backups/bot-before-update.sqlite'"
   ```

   Убедитесь, что резервная копия существует, доступна только администратору и находится вне каталогов, заменяемых обновлением. Если текущая БД находится в другом месте, **замените путь до выполнения команды**. Не копируйте открытый `*.sqlite` обычным `cp` вместо резервного API. Плановые копии ограничены `backup.max_copies`; сохранение/удаление ручных копий контролирует оператор.

4. **Получить нужное обновление без потери локальных данных.** Убедившись, что `git status --short` не показывает неожиданных изменений:

   ```bash
   git fetch origin
   git pull --ff-only origin restore/verified-691-tests
   ```

   В команде указан пример обновления **этой** ветки; для выпуска используйте согласованную ветку/тег. При конфликте или отказе `--ff-only` не применяйте принудительные команды: разберите изменения отдельно.

5. **Обновить зависимости и проверить конфигурацию.** Из каталога проекта:

   ```bash
   .venv/bin/python -m pip install -r requirements.txt
   .venv/bin/python -m bot.doctor
   ```

   Сохраните личные настройки и секреты. Проверка не должна печатать токен или персональные ID. После реализации новая версия обязана поддерживать параметры из §18 ТЗ.

6. **Запустить сервисы только после подтверждения готовности v1.** Команды выполняет администратор:

   ```bash
   sudo systemctl start tgbot-worker.service tgbot.service
   sudo systemctl status tgbot-worker.service tgbot.service --no-pager
   sudo systemctl show tgbot-worker.service -p IPAddressDeny
   ```

   Ожидается, что оба сервиса запущены и запреты присутствуют; одного вывода `systemctl show` **недостаточно**. Обязательны фактическая проверка запрета доступа worker к `127.0.0.1`, проверка DNS/HTTPS при действующей защите и интеграционная приёмка постоянного worker. При их провале не допускайте незащищённую загрузку.

7. **Проверить журнал и работу бота.**

   ```bash
   sudo journalctl -u tgbot.service -u tgbot-worker.service -n 100 --no-pager
   ```

   Убедитесь в отсутствии критических ошибок, корректном восстановлении задач, ответе бота, сообщении администратору о запуске (когда Telegram доступен) и отсутствии секретов в журнале.

8. **Откат при ошибке.** Остановите оба сервиса, сохраните диагностику, верните проверенный коммит/релиз по записанному SHA с учётом локальных изменений. **Не восстанавливайте старую SQLite автоматически:** откат схемы может быть несовместим. Восстановление копии допускается только по решению оператора после предупреждения, что изменения БД после момента резервного копирования будут потеряны. Не удаляйте готовые пользовательские файлы для «очистки» при откате.

## Приёмка перед публичным запуском

Приёмка обязательна **в постоянном `tgbot-worker.service`**, не только во временном тестовом systemd unit. Проверяются запрет loopback для worker и его дочерних процессов, DNS/HTTPS/Fake-IP на целевых серверах, строгая проверка исходных URL, изоляция `inspect`, две кнопки при неизвестных качествах, отмена дерева процессов, одна активная загрузка, SQLite только у бота, восстановление без дублей, готовые файлы, квоты, кэш, Telegram local/cloud и резервные копии. Применяются критерии §21 ТЗ и §10 политики; результат отмечается PASS/FAIL/INCONCLUSIVE, не объявляется успешным без проверки.

**Никаких** динамических `systemd-run` в рабочем коде, незащищённого fallback, подключения дополнительного Docker/брокера или изменения системного DNS ради v1.
