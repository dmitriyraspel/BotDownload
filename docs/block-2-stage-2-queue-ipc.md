# Блок 2 / Этап 2 — интеграция очереди и IPC (эксперимент)

Актуальные требования безопасности v1: [SECURITY_POLICY_V1.md](SECURITY_POLICY_V1.md).
Этот документ описывал ранний fail-closed прототип; ниже учтён добавленный
после него маршрут экспериментального исполнения медиа.

Реализован `bot.media_queue_dispatcher`, явный тестовый маршрут
SQLite `queued` → `downloading` → lease `offered` →
IPC `reserve` → lease `running` → `execute_media` → при успехе
проверка и публикация файла (`upload_pending`), при ошибке — отзыв lease
и `failed`.

Диспетчер последователен: не запускает одновременно несколько задач.
Резервирование подтверждает только worker с проверенным Unix peer UID
и токеном lease; отменённая или просроченная задача не запускается.
На ошибках происходит отзыв IPC-резервации, задача помечается failed,
файл не публикуется.

**Текущий статус:** `execute_media` добавлен для отдельного интеграционного
теста и использует изолированный запуск yt-dlp, Unix gateway и проверку
lease. Однако испытания реальной сети, защиты только от loopback по v1,
отмены, лимитов и восстановления ещё не завершены. Диспетчер **не
подключён к production Telegram polling**; этот путь нельзя считать
разрешением на скачивание или отправку пользовательских медиа.

Тесты: `tests/test_media_queue_dispatcher.py`, плюс полный pytest.
Для отдельной тестовой SQLite можно явно вызвать
`run_media_dispatcher(stop=..., db_path=..., socket_path=..., configured_download_dir=...)`.
Нельзя передавать ему production SQLite до завершения приёмки: в
экспериментальном режиме он действительно пытается скачать медиа.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m bot.main
```

Следующий обязательный рубеж до **production-включения**:
подтвердить loopback-блокировку по `SECURITY_POLICY_V1.md`,
ресурсные лимиты, отмену/восстановление и полный цикл Telegram.
