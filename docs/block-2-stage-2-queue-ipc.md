# Блок 2 / Этап 2 — интеграция очереди и IPC (fail-closed)

Реализован `bot.media_queue_dispatcher`, явный тестовый маршрут
SQLite `queued` → `downloading` → lease `offered` →
IPC `reserve` → lease `running` → отзыв lease и `failed`.

Диспетчер последователен: не запускает одновременно несколько задач.
Резервирование подтверждает только worker с проверенным Unix peer UID
и токеном lease; отменённая или просроченная задача не запускается.
На ошибках происходит отзыв IPC-резервации, задача помечается failed,
файл не публикуется.

**Почему нет исполнения медиа:** сетевой egress sandbox, проверка
redirect/CDN/secondary URL и суммарная квота записи ещё не реализованы.
Поэтому протокол намеренно не содержит `execute_media`, а новый
диспетчер **не подключён к production Telegram polling**. Иначе
промежуточный этап создал бы небезопасные загрузки или отправлял
пользователям фикстуры. Этот этап завершает именно очередь и IPC
резервирование, но не полную цепочку скачивания.

Тесты: `tests/test_media_queue_dispatcher.py`, плюс полный pytest.
Для отдельной тестовой SQLite можно явно вызвать
`run_media_dispatcher(stop=..., db_path=..., socket_path=...)`.
Нельзя передавать ему production SQLite: задачи намеренно fail-closed.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m bot.main
```

Следующий обязательный технический рубеж до реального скачивания:
изолированный сетевой исполнитель с контролем всех outbound запросов
и ограничением суммарного объёма записи.
