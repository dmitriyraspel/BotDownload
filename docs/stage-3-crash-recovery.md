# Этап 3 — аварии и восстановление

## Сценарии и инварианты

1. **Неожиданный выход supervised worker.** `bot.main` дожидается
   `worker.wait()`, затем `reconcile_confirmed_worker_exit` в одной
   транзакции отзывает все offered/running leases и переводит связанные
   downloading/processing задачи в failed. Повторный вызов идемпотентен.
   Очередь новых задач не затрагивается. Бот завершает работу с ошибкой.
2. **Истёкший lease.** Периодическое обслуживание очереди помечает
   lease expired и соответствующую задачу failed. Повторного запуска нет.
3. **Перезапуск бота.** До запуска worker вызывается
   `recover_before_workers`. Задачи с lease не переисполняются,
   даже если lease ещё не истёк: после перезапуска нельзя доказать,
   что отдельный worker уже прекратил работу. После истечения lease
   они переходят в failed. Непереданные worker задачи по прежнему
   возвращаются в queued.
4. **Прерванная отправка Telegram.** `uploading` сохраняется без
   автоматического повтора: Telegram мог принять файл до аварии.
   Разрешение требует ручной сверки; нельзя автоматически списывать
   квоту или повторно отправлять файл.
5. **Файлы.** Готовые файлы проверяются, отсутствующие/небезопасные
   помечаются как failed, неизвестные каталоги только перечисляются,
   но не удаляются.

## Ограничение
`reconcile_confirmed_worker_exit` допустимо вызывать **только после
подтверждённого завершения процесса worker**. Для неизвестного внешнего
worker оно небезопасно. При восстановлении после падения самого бота
используется консервативный путь по lease/TTL.

## Проверки
`python -m pytest -q tests/test_worker_crash_recovery.py tests/test_startup_recovery.py tests/test_cancel_worker_lifecycle.py tests/test_queue_maintenance.py`

Реальные скачивания отключены. Никакие offline-фикстуры не отправляются
пользователям Telegram.
