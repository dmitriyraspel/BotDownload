# Финальная интеграция — этап 4

## Статус и границы
Ветка `feature/stage-2-telegram` объединяет четыре этапа:
очередь/диспетчер, отмену, восстановление и supervision процессов.

**Единственная команда запуска** под непривилегированным пользователем
`tgbot` на Debian 12 / Python 3.11:

```bash
cd /opt/BotDownload
.venv/bin/python -m bot.main
```

Без systemd. Запуск вызывает восстановление SQLite, запускает
изолированный offline IPC worker, Telegram polling, очередь отправки
и обслуживание очереди. Завершение polling останавливает фоновые задачи
и worker; неожиданный выход worker или фонового сервиса приводит к
завершению бота с ошибкой. Утечки IPC-сокета предотвращает supervisor.

## Проверки
```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m bot.main
```

Проверяются в том числе:
- `tests/test_stage4_lifecycle.py`: штатная остановка и авария
  обслуживания очереди с очисткой остальных процессов;
- `tests/test_stage4_integration.py`: повторный рестарт,
  отзыв lease после подтверждённого выхода worker, отсутствие
  дублирующего запуска;
- тесты этапов 1–3: последовательный IPC, отмена и истечение lease.

## Ограничения
Медиа-загрузки **не включены**. Offline-диспетчер работает только
с отдельной тестовой SQLite и никогда не подключается к Telegram polling.
Тестовая фикстура не является скачанным медиа и не должна отправляться
пользователям. Задачи `uploading` после аварии требуют ручной сверки,
поскольку доставка Telegram может быть неоднозначной.

Включение реальных загрузок — отдельный этап с отдельным разрешением.
